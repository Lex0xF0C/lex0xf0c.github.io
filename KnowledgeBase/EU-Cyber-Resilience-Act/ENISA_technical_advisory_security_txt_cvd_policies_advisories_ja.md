## 範囲とコンテキスト

デジタル要素を含む製品の製造者は、脆弱性に関する情報を受信、評価、および伝達するための実践的な方法を必要としています。明確な報告チャネル、構造化された開示プロセス、および適時なセキュリティコミュニケーションは、効果的な脆弱性管理の重要な要素です。このコンテキストにおいて、security.txt、協調的な脆弱性開示（CVD）、セキュリティアドバイザリなどのツールやプラクティスは、組織が一貫性があり透明性のある方法で脆弱性情報を扱うのに役立ちます。

サイバーレジリエンス法（CRA）は、デジタル要素を含む製品の製造者に対して新たな脆弱性管理の義務を導入しています。中小企業 (SME) は、特にサイバーセキュリティ、コンプライアンス、または法的リソースが限られている場合、これらの義務を実行に移すための実践的なガイドと支援を必要とする可能性があります。本パッケージは、組織が自らのニーズや成熟度レベルに合わせて調整できる、実践的で即時に使用可能なテンプレートを提供します。また、CRA の脆弱性管理要件および CEN/CLC/JTC13 によって策定中の脆弱性処理に関する整合規格 EN 40000-1-3 の実践的な適用を支援します。

本 ENISA テクニカルアドバイザリの目的は、デジタル要素を含む製品の製造者、特に SME に対し、CRA の脆弱性管理要件に沿った脆弱性報告、協調的な開示、およびセキュリティコミュニケーションのプラクティスを実装するための実践的な支援を提供することです。

特に、本パッケージは以下を提供します。
* security.txt が、外部の当事者が脆弱性を報告する場所と方法を特定するのにどのように役立つかを説明する。
* 脆弱性報告の受付、評価、および管理のための CVD プラクティスの使用を支援する。
* ユーザーに脆弱性、緩和策、および修正を伝達するためのセキュリティアドバイザリのテンプレートを提供する。
* 組織が規制上および標準に基づく期待事項を実践的な手順に変換するのを支援する。

本パッケージの範囲は、脆弱性報告、協調的な開示、および外部セキュリティコミュニケーションのための文書やプロセスの実践的な使用に限定されています。組織が連絡先情報を公開し、着信報告を扱い、報告者と伝達を取り、関連する脆弱性と是正についてユーザーに通知する方法に焦点を当てています。

本パッケージは法的助言を提供するものではなく、CRA に関する公式ガイドラインに代わるものではありません。また、セキュア開発、内部の是正ワークフロー、インシデント対応、サードパーティサプライヤーによる脆弱性処理など、脆弱性管理や製品セキュリティのすべての側面を網羅しているわけではありません。これらのトピックは引き続き重要ですが、本パッケージの主な範囲外となります。

**NIS2 における関連性:** 一部の製造者は、指令 (EU) 2022/2555 (NIS2) の対象でもあります。原則として、附属書 I および II に設定されたセクターのエンティティのタイプとして記載されている中規模および大規模企業は、NIS2 の適用範囲に入ります。特に、附属書 II の第5項は「製造」セクターをカバーしています。サイバーセキュリティリスク管理義務の一環として、第21条(2)(e) NIS2 は、範囲内のエンティティに対し、自社のネットワークおよび情報システムに対する脆弱性処理と開示に対処することを求めています。1つの security.txt ファイルと1つの監視された報告チャネルで、CRA と NIS2 の両方に対応できます。ただし、CVD ポリシーでは、報告が CRA 第14条に基づいて通知された自社のデジタル要素を含む製品に関するものか、NIS2 第23条に基づいて通知されたネットワークおよび情報システムに関するものかを明確にする必要があります。

## 1. security.txt、CVD ポリシー、セキュリティアドバイザリ

CRA は、デジタル要素を含む製品の製造者に対し、製品のサポート期間中に脆弱性を処理するためのプロセスを確立することを求めています。これには、協調的な脆弱性開示（CVD）ポリシーの導入と適用、脆弱性を報告するための連絡メカニズムの提供、および修正された脆弱性に関する情報の公開が含まれます。規則が適用される法的義務を確立し、今後の整合規格（現在策定中の prEN 40000-1-3）がさらなる技術的要件とガイドを提供することを意図している一方で、本パッケージは、製造者（特に SME）が遅滞なく脆弱性に対処し是正するのを支援すると同時に、将来の整合規格の適用を促進する即時利用可能な成果物（アーティファクト）を提供することで、実装のギャップを埋めることを目的としています。

| 内容 | なぜ必要か |
| :--- | :--- |
| **security.txt** | 脆弱性を報告するための連絡先アドレスを提供し（CRA 附属書 I、第 II 部、第6項）、単一の連絡窓口を容易に特定できるようにするための実践的な手段（CRA 第13条(17)）。その公開はドラフト prEN 40000-1-3 で推奨されています。本文書は利用可能なフィールドを含む追加情報を提供します。 |
| **協調的な脆弱性開示 (CVD) ポリシー** | CRA 附属書 I、第 II 部の脆弱性処理要件では、製造者が誰でも安全に脆弱性を報告できるようにするポリシーを導入し適用することを規定しています。 |
| **セキュリティアドバイザリ** | CRA 附属書 I、第 II 部の脆弱性処理要件は、製造者に対し、修正された脆弱性に関する情報を共有し公開することを求めており、ユーザーは何が修正されたかを知り、必要に応じて行動を起こすことができます。 |

### 1.1 security.txt
security.txt は、組織がセキュリティ連絡先情報を公開するための標準化された方法を提供し、セキュリティ研究者が脆弱性を報告しやすくします。RFC 9116 で定義されており、発見可能な連絡窓口と、該当する場合は関連する脆弱性開示ポリシーへのリンクを提供することにより、脆弱性報告を支援します。本文書の 4.1 節では、即時デプロイ可能な security.txt テンプレートを提供しています。テンプレートを適応させてデプロイするには:

1. 提供された即時デプロイ可能なファイルをコピーし、プレースホルダーを実際の連絡先とポリシーの URL に置き換えます。PGP 鍵が設定されている場合のみ、PGP 鍵のリンクを含めます。
2. 安定したロールベースの連絡先アドレスと URL（例: `security@yourdomain.example` および `/security`）を使用します。単一の連絡窓口は、ユーザーへの情報と指示（CRA 附属書 II、第2項）にも記載する必要があり、製品のライフサイクル全体にわたって有効であり続ける必要があります。
3. `https://yourdomain.example/.well-known/security.txt` にアップロードします。`/.well-known/` パスは必須であり、オプションではないことに注意してください。
4. `Expires` フィールドを12か月以内に設定し、更新のためにカレンダーにリマインダーを設定します。

### 1.2 CVD ポリシー
協調的な脆弱性開示（CVD）ポリシーは、セキュリティ研究者やその他の外部当事者から組織が脆弱性報告をどのように受信、評価、管理するかを説明します。脆弱性を報告する方法、報告者が組織に何を期待できるか、および開示プロセスを通じて情報がどのように伝達されるかを明確にします。4.2 節では、即時デプロイ可能な CVD ポリシーテンプレートを提供しています。テンプレートを適応させてデプロイするには:

1. かっこで囲まれたすべてのプレースホルダー（会社名、範囲内の製品、連絡用メールアドレス、応答時間の数値（デフォルト値が提供されています。エンジニアリング機能に基づいて調整してください））を置き換えます。
2. 範囲リストが、まだサポートされているファームウェア/ソフトウェアバージョンを含め、実際の製品範囲と一致していることを確認します。
3. 完成したポリシーをウェブサイトで公開し、security.txt ファイルからリンクします。
4. 指名されたポリシーオーナーを1名、代理人を少なくとも1名割り当て、個人メールではなく共有のロールベースのメールボックスを使用し、年次レビューのカレンダーリマインダーを設定します。
5. 必要な社内プロセスと責任を通じて、ポリシーが実際に適用されることを確認します。公開だけでは不十分です。

### 1.3 セキュリティアドバイザリ
セキュリティアドバイザリは、製品に影響を与えるセキュリティ脆弱性、その潜在的な影響、およびリスクを低減するためにユーザーが取ることができる手順について通知します。製造者が、利用可能な修正、アップデート、または緩和策を含め、関連するセキュリティ情報を明確かつ迅速に伝えるのに役立ちます。

他の2つの成果物とは異なり、アドバイザリテンプレートは一度カスタマイズするだけでなく、脆弱性が修正され開示されるたびに再利用されます。フォーマットがチームで機能することを確認すること以外に、事前に入力するものは何もありません。各個別のアドバイザリは、4.3 節のフィールドを使用して開示の時点で入力されます。

1. 修正がリリースされた後にアドバイザリを公開する責任者を社内で合意します。
2. 影響を受ける顧客にどのように通知するかを決定します。顧客が判明している場合は、顧客ポータル、サービスチャネル、直接通知などを通じて直接通知します。判明していない場合は、ウェブサイトの専用ページでアドバイザリを公開します。どちらの場合も、公開されたすべてのアドバイザリの公開インデックスを維持します。選択するチャネルは、製品に関連する労力とリスクを考慮して適切なものである必要があります。
3. 今後解決されるすべての脆弱性について、カスタマイズされ合意されたテンプレート（汎用テンプレートについては 4.3 節を参照）を使用します。

## 2. 一般的な間違い

いくつかの単純な間違いにより、脆弱性報告と処理の効率が低下する可能性があります。次の表は、SME が security.txt の設定、脆弱性報告の処理、および顧客へのセキュリティ上の問題の伝達の際に直面する可能性のある一般的な問題と、それらを回避するための実践的な方法を示しています。

| 一般的な間違い | 何が問題になり得るか？ | 回避する方法 |
| :--- | :--- | :--- |
| **security.txt** | | |
| **ファイルの場所が間違っている** | 研究者がファイルを見つけられない。 | `/.well-known/security.txt` で公開する。 |
| **ファイルにアクセスできない** | ログイン、CAPTCHA、またはファイアウォールがアクセスをブロックする。 | ファイルが公開アクセス可能であることを確認する。 |
| **不適切なフォーマットまたは必須フィールドの不足** | ツールがファイルを正しく読み込めない可能性や、RFC 9116 の要件を満たさない可能性がある。 | プレーンテキスト、UTF-8 エンコーディング、および有効な `Contact` と `Expires` フィールドを使用する。 |
| **リンク切れまたは HTTPS エラー** | 研究者がファイルにアクセスできないか、そのリンクをたどることができない。 | HTTPS を使用してファイルとリンクをテストする。 |
| **期限切れまたは不正確な連絡先詳細** | 報告が適切な人に届かない可能性がある。 | 監視されている連絡先アドレスを使用し、定期的にファイルを更新する。 |
| **不明確またはリンク切れのポリシーリンク / 担当者が割り当てられていない** | 研究者が脆弱性の報告方法やカバーされているシステムを知らない。ファイルが古くなり、報告に返答がなくなる。 | 明確でアクセス可能な脆弱性開示ポリシーにリンクする。ファイルの維持と報告の監視を担当する者を割り当てる。 |
| **ファイルだけで十分であると仮定する** | 報告は届くが、組織はそれをどのように処理すればよいか分からない。 | 脆弱性を評価、修正、および追跡するためのプロセスを確立する。 |
| **協調的な脆弱性開示 (CVD)** | | |
| **明確な報告チャネルがない** | 研究者が脆弱性をどこに報告すればよいか分からない。 | 明確で監視されている報告チャネルを提供する。 |
| **受領確認がない** | 研究者は自分たちの報告が受信されたかどうか分からない。 | 報告を受領確認し、次の手順を説明する。 |
| **割り当てられた責任がない** | 報告が見落とされたり、未解決のままになったりする。 | 可能であればバックアップを用意し、各報告の管理責任を割り当てる。 |
| **優先順位付けがない** | 深刻な脆弱性に迅速に対処できない可能性がある。 | 深刻度と潜在的な影響を評価し、それに応じて優先順位を付ける。 |
| **報告者との協調がない** | ユーザーが自分自身を保護できるようになる前に、脆弱性の詳細が開示される可能性がある。 | 報告者に最新情報を伝え、合理的な開示タイムラインに合意する。 |
| **是正プロセスがない** | 脆弱性が報告されても未修正のままになる。 | 問題の調査、修正、および検証の責任を割り当てる。 |
| **記録やフォローアップがない** | アクションや期限が忘れられ、報告がオープンなままになる。 | 報告、決定、アクション、およびその状態を追跡する。 |
| **報告でアクティブな悪用がチェックされない** | CRA 第14条に基づく24時間以内の早期警告が見逃される。 | 着信するすべての報告にアクティブな悪用の兆候がないか確認し、単一報告プラットフォームを介して誰が通知を送信するかを定義する。 |
| **サードパーティコンポーネントの脆弱性がサプライヤーに報告されない** | サプライヤーに通知されず、修正が遅れる。 | 利用可能な場合はその CVD ポリシーに従い、コンポーネントの製造者またはメンテナに報告を転送する（CRA 第13条(6)）。 |
| **セキュリティアドバイザリ** | | |
| **不明確な脆弱性の説明** | ユーザーが問題やその潜在的な影響を理解できない。 | 明確でシンプルな言葉で脆弱性を説明する。 |
| **影響を受けるバージョンが特定されていない** | ユーザーは自分の製品が影響を受けるかどうかを判断できない。 | 影響を受けるバージョンと、判明している場合は影響を受けないバージョンを一覧表示する。 |
| **深刻度や影響の情報がない** | ユーザーはどれほど緊急に行動する必要があるかを判断できない。 | 影響を説明し、適切な場合は深刻度を示す。 |
| **修正または緩和の指示がない** | ユーザーは問題について知っているが、自分自身を保護できない。 | 修正が利用できない場合は、アップデート指示または回避策を提供する。 |
| **リンク切れまたは連絡先の詳細の欠落** | ユーザーが修正を見つけられないか、ヘルプを求めることができない。 | アップデートへの機能するリンクと、質問のための連絡先を含める。 |

## 3. グッドプラクティスとテンプレート

### 3.1 security.txt 実装ガイド
security.txt ファイルの公開は、セキュリティ研究者が組織に脆弱性を報告する方法を素早く特定できるようにする推奨されるプラクティスです。ウェブサイト上で公開され、関連するセキュリティ連絡先情報を含むこのシンプルなテキストファイルは、世界中のセキュリティ研究者に適切な報告チャネルを見つけるための標準化された方法を提供します。これにより、適切なコミュニケーションチャネルを見つけようとして貴重な時間が失われないようにし、脆弱性報告の遅延を減らすのに役立ちます。

実装が簡単であるにもかかわらず、security.txt の導入率は依然として限られています。ドイツ連邦情報セキュリティ庁（BSI）およびフランスの公的データプラットフォーム（datagouv）による最近の測定では、調査対象のウェブサイトのわずかな割合でしか有効なファイルが見つからず、より広範な導入の明確な機会があることが強調されています。

ドラフト prEN 40000-1-3 は security.txt ファイルの公開を推奨していますが、何を含めるべきかの詳細には踏み込んでいません。security.txt は実際には自立した正式な IETF 標準（RFC 9116）であるため、フィールドリストは既に存在しており、それを記入して正しくホストする必要があります。

#### 3.1.1 配置場所
プライマリドメイン（および範囲内製品に関連するすべてのドメイン、例: クラウドコンパニオンアプリ）のまさにこのパスでファイルをホストします。
`[https://yourdomain.example/.well-known/security.txt]`

*注:* `/security.txt` だけに配置しないでください。RFC 9116 は `/.well-known/` パスを要求します。サイトルートにもコピーを配置することは可能ですが、RFC 9116 で定義されているように、ファイルは少なくとも `/.well-known/security.txt` で利用可能にする必要があります。

HMI やエッジデバイスなどの組み込みウェブサーバーを持つ製品は、ユーザーやセキュリティ研究者を製造者の脆弱性開示情報に誘導する必要があります。適切な場合、デバイスのウェブインターフェースまたは製品文書は、製造者の security.txt ファイルまたは脆弱性開示ポリシーへのリンクを提供できます。デバイス自体のウェブインターフェース用に個別の security.txt ファイルを公開する場合、その範囲と連絡先の詳細は明確で最新の状態に保つ必要があります。

#### 3.1.2 ホスティング要件

| 要件 | 意味 |
| :--- | :--- |
| **`/.well-known/security.txt` に存在しなければならない** | security.txt ファイルは、RFC 9116 および RFC 8615 に従って `/.well-known/security.txt` でホストされなければなりません。古いツールとの互換性が必要な場合は、ウェブサイトのルート (`/security.txt`) にもコピーを用意できます。ただし、この場所は独立したバージョンのファイルをホストするのではなく、`/.well-known/security.txt` にリダイレクトする必要があります。 |
| **両方の場所が存在する場合、`/.well-known/` が優先される** | ルートの場所と `/.well-known/` の場所の両方が利用可能な場合、`/.well-known/` の下でホストされているバージョンが正当とみなされます。したがって、一方のファイルが更新され、もう一方が更新されない場合に矛盾が生じる可能性があるため、別々のコピーを維持することは推奨されません。ルートの場所から `/.well-known/security.txt` へのリダイレクトを実装することで、単一の正当なバージョンのみが維持されるようになります。 |
| **HTTPS 経由で提供されなければならない** | security.txt ファイルは HTTPS 経由で提供されなければなりません。暗号化されていない HTTP 経由での配信は RFC 9116 に準拠していません。 |
| **`Content-Type: text/plain; charset=utf-8` で提供されなければならない** | security.txt ファイルは HTTP 応答ヘッダー `Content-Type: text/plain; charset=utf-8` で配信されなければなりません。一部のホスティングプロバイダーがプレーンテキストファイルに誤ったコンテンツタイプを自動的に割り当てるため、この要件は見落とされがちです。したがって、アップロード時に正しいコンテンツタイプが適用されたと仮定するのではなく、ホスティング構成の検証が推奨されます。デプロイ後、`curl -i https://yourdomain.example/.well-known/security.txt` を実行し、レスポンスに `Content-Type: text/plain; charset=utf-8` が含まれていることを確認することで構成を検証できます。 |
| **リダイレクトは許可されるが精査される** | security.txt ファイル、またはその中で参照されているリソース（セキュリティポリシーページや、公開されている場合は PGP 公開鍵など）にアクセスする際のリダイレクトは許可されます。ただし、リダイレクトは追加の信頼とセキュリティの考慮事項をもたらす可能性があるため、security.txt ファイルおよび参照されるリソースを組織の管理下にあるインフラストラクチャ上でホストすることがベストプラクティスとみなされます。また、信頼を低下させ、不必要なセキュリティ上の懸念をもたらす可能性があるため、サードパーティの URL 短縮サービスや無関係なドメインを使用するのではなく、信頼できるリソースを直接指すように連絡先および暗号化リンクを設定することが推奨されます。 |

#### 3.1.3 フィールド別テンプレート

| フィールド | 必須か？ | 目的 |
| :--- | :--- | :--- |
| **Contact** | 必須 | 連絡方法: メール、電話、または連絡先ページの URL。複数リストできます。最初にリストされたものが優先される方法であるため、最善のオプションを最初に配置します。 |
| **Expires** | 必須 | ファイルの「有効期限」日付。忘れられた古いファイルが静かにデッドインボックスに研究者を送信するのを防ぎます。12か月以内に保ち、カレンダーに更新リマインダーを設定します。 |
| **Encryption** | オプション（Contact がメールの場合は推奨） | PGP 鍵がある場合は、そのリンク。そこに鍵自体を貼り付けないでください。 |
| **Policy** | オプション（有益） | 完全な CVD ポリシーへのリンク。研究者が何かを報告する前にプロセスを理解できるようにします。 |
| **Canonical** | オプション | この正確なファイルの標準（カノニカル）URL。これがないと、異例な場所にホストされているコピーを見つけた人が、それが正当か改ざんされたものかを判断できません。 |
| **Acknowledgments** | オプション | 研究者の名前を挙げて感謝するクレジットページへのリンク: 公開するのではなく、あなたに報告するための本当のインセンティブとなります。 |
| **Preferred-Languages** | オプション | 報告を処理できる言語（例: `en`, `de`, `ja`）。 |

RFC 9116 は、OpenPGP クリアテキスト署名を使用して security.txt ファイルにデジタル署名することを推奨しています。ただし、デジタル署名は必須ではなく、追加の鍵管理と署名検証の考慮事項が必要です。SME は、署名を正しく実装および維持するために必要な能力があるかどうかを評価する必要があります。これらの能力が利用できない場合は、RFC 9116 に従って、正確でアクセス可能であり、定期的に維持されている security.txt ファイルの公開に優先順位を付ける必要があります。

#### 3.1.4 即時デプロイ可能なファイル
ブロックを `security.txt` という名前のプレーンテキストファイル（`.txt.txt` なし、BOM なし、Unix 改行）にコピーし、プレースホルダーを置き換えて、ウェブサーバーの `/.well-known/` にアップロードします。PGP 鍵が設定されていない場合の Encryption 行を含め、組織で使用されていないオプションのフィールドはすべて削除します。

```text
Contact: mailto:security@yourdomain.example
Contact: https://yourdomain.example/security/report
Encryption: https://yourdomain.example/.well-known/pgp-key.asc
Expires: 2027-07-27T00:00:00.000Z
Acknowledgments: https://yourdomain.example/security/hall-of-fame
Policy: https://yourdomain.example/security/disclosure-policy
Preferred-Languages: en, ja
Canonical: https://yourdomain.example/.well-known/security.txt
```

*注:* `Expires` を12か月以内に設定し、更新のためにカレンダーリマインダーを設定します。期限切れのファイルは、連絡先の詳細が古い可能性があることをスキャナーや研究者に示します。

#### 4.2.2 実装上の注意点
* CVD ポリシーは、支援技術を使用して読み取りおよびナビゲートできるアクセシブルなウェブページなど、アクセス可能な形式で公開します。
* 「報告方法」セクションには、脆弱性の報告に使用できる1つ以上の連絡メカニズムを含めます。これらには、専用のメールアドレス、ウェブフォーム、チケッティングポータル、電話番号、またはその他の適切な報告チャネルが含まれます。可能な場合は、複数の感覚チャネルを通じてアクセスできるオプションを提供します。
* 着信するすべての報告にアクティブな悪用の兆候がないか確認します。製造者が自社製品においてアクティブに悪用されている脆弱性を認識した場合、24時間以内の早期警告から始めて、単一報告プラットフォームを介してコーディネーターとして指定された CSIRT および ENISA に通知し、影響を受けるユーザーに通知する必要があります（CRA 第14条）。これを誰が評価し、誰が通知を提出するかを事前に定義します。
* ポリシー内の目標時間は例であり、製品に対して現実的である必要があります。機械やその他の OT 製品の場合、修正には安全機能を含む再検証が必要になる場合があり、計画メンテナンス中にしかインストールできないことがよくあります。修正にポリシー目標時間よりも長い時間がかかる場合は、まず緩和策または支援措置を提供します（CRA に関する欧州委員会 FAQ 質問 4.3.1 を参照）。CVSS は深刻度を表すものであり、特定の運用環境におけるリスクを表すものではありません。
* セーフハーバー声明は、製造者自体のシステムのテストのみを許可し、製造者自体の主張のみを放棄することができます。サードパーティが所有するシステムのテストを許可することはできず、その範囲を超える活動に対する責任を排除することはできません。法律上の状況は加盟国によって異なります。報告者と製造者の両方が、開示プロセスにおいて責任を負います。

#### 4.3.2 実装上の注意点
* 協調的な開示日に達したら、解決された脆弱性ごとにセキュリティアドバイザリを公開します。公開されたすべてのアドバイザリの公開アクセス可能なインデックスを維持します。これは脆弱性開示活動の明確な記録を提供し、継続的なコンプライアンスの証拠をサポートします。
* 2つのケースを区別します。修正された脆弱性に関する情報は、セキュリティアップデートが利用可能になった時点で公開されます。正当な理由がある場合は、ユーザーがパッチを適用する機会を得るまで公開を遅らせるオプションがあります（CRA 附属書 I、第 II 部、第4項）。脆弱性がアクティブに悪用されている場合、修正が利用可能になる前であっても、必要に応じて補完的対策を用いて、CRA 第14条(8)に従って影響を受けるユーザーに通知する必要があります。
* 支援技術を使用して読み取りおよびナビゲートできるアクセシブルなウェブページなど、アクセス可能な形式でセキュリティアドバイザリを公開します。
* 人間が読めるアドバイザリに加えて、組織は実行可能な場合、CSAF などの機械可読な形式でアドバイザリを公開し、自動化された配信フィードを通じて利用可能にする必要があります。CRA 第14条(8)は、適切な場合、構造化された機械可読な形式でのユーザー情報を求めています。CSAF は ISO/IEC 20153:2025 として標準化されており、その VEX プロファイルにより、製品が影響を受けないという声明を公開できます。独自の CSAF インフラストラクチャを運用したくない組織は、利用可能な場合、コーディネーターまたはセクター CERT が提供する公開サービスを使用できます。

### A.1 本パッケージが CRA の義務をどのように支援するか
規則 (EU) 2024/2847、附属書 I、第 II 部は、デジタル要素を含む製品に対する8つの脆弱性処理要件を設定しています。本パッケージで提供されるテンプレートは、これらの要件の実装を支援しますが、対応する義務を単独で果たすものではありません。関連するプロセスも実行に移す必要があります。以下の表は、本パッケージで支援されていない要件を含め、すべての要件を網羅しています。

| CRA 附属書 I、第 II 部要件（要約） | 支援状況 |
| :--- | :--- |
| **(1) 脆弱性とコンポーネントを特定し文書化する（例: ソフトウェア部品表 (SBOM)）** | 本パッケージでは支援されていません。 |
| **(2) 機能アップデートとは別にセキュリティアップデートを提供することを含め、技術的に実現可能な場合、不当な遅延なく脆弱性に対処し是正する** | **CVD ポリシーテンプレート:** 報告された脆弱性を処理するための応答時間と是正目標、および構造化されたプロセスを確立します。不当な遅延なく脆弱性が評価され是正されることを確保するために、これらのプロセスを導入し遵守する必要があります。 |
| **(3) 製品のセキュリティについて効果的かつ定期的なテストとレビューを適用する** | 本パッケージでは支援されていません。パブリック向けの成果物ではなく、内部のエンジニアリングプロセスです。 |
| **(4) 修正された脆弱性に関する情報を公開する** | **CVD ポリシーテンプレート:** 開示の調整を支援します。<br>**セキュリティアドバイザリテンプレート:** 修正された脆弱性と是正情報を伝達するための一貫した構造を提供します。製造者は、脆弱性が修正されセキュリティアップデートが利用可能になったときに、関連するアドバイザリを準備して公開する必要があります。 |

#### ドラフト prEN 40000-1-3 との関係
* **security.txt ガイダンス:** ドラフトで推奨されている security.txt ファイルの公開を実装しています。
* **CVD ポリシーテンプレート:** ドラフトが CVD ポリシーに求める要素、すなわち連絡メカニズム、受領確認・応答・更新のタイムフレームを含む伝達への期待事項、第三者と情報を共有するための条件、エンバーゴ期間を含む公開開示の調整、報告内容への期待事項、範囲、公開プラクティス、および報告者のクレジット表記をカバーしています。
